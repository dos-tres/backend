# data_check — 온통청년 Open API 데이터 점검

> 로컬 `ai_hackathon` 폴더에서 옮겨 온 문서다. 경로는 저장소 구조 기준으로 바꿨다 (2026-11-19). 추천 전체 흐름은 [RECOMMENDATION.md](RECOMMENDATION.md). 조사 스크립트: `tools/data_check/`.

온통청년(youthcenter.go.kr) Open API 두 종의 실제 응답 형식을 확인하고, 청년센터 홈페이지를 어떤 방식으로 크롤링해야 할지 진단하는 스크립트 모음이다.

> 진행 기록 · 마지막 실행 2026-11-18

## 실행 방법

```bash
cp .env.example .env      # 키 2개 입력 (정책 API, 센터 API는 키가 따로 발급됨)
python tools/data_check/inspect_policies.py            # 전국 정책 전체 (지역 제한: python tools/data_check/inspect_policies.py 11000)
python tools/data_check/inspect_centers.py             # 센터 목록 + 홈페이지 접속 진단
python tools/data_check/inspect_centers.py --no-web    # 홈페이지 진단은 건너뜀
```

표준 라이브러리만 사용한다. Windows 콘솔에서 한글이 깨지면 `PYTHONIOENCODING=utf-8`을 붙인다.
결과는 `data/runtime/data_check/`에 저장된다(gitignore 대상).

| 파일 | 내용 |
|---|---|
| `common.py` | .env 로딩, 페이지 단위 수집, 필드 프로파일 |
| `inspect_policies.py` | `getPlcy` → `data/runtime/data_check/policy/` |
| `inspect_centers.py` | `getSpace` + 홈페이지 진단 → `data/runtime/data_check/center/` |
| [`POLICY_FIELDS.md`](POLICY_FIELDS.md) | **정책 API 필드 정의, 코드 구조(지역·기관·정책번호), 코드표** |
| [`CENTER_FIELDS.md`](CENTER_FIELDS.md) | **센터 API 필드 정의, 지역코드 조합, 주소·URL 정리 규칙** |

## 지역 매칭 설계

서비스 목표: **사용자의 지역을 받아 그 지역의 정책과 센터 프로그램을 추천한다.**

### 정책과 센터를 서로 연결해야 하나? → 아니다

두 API 모두 **각자 지역코드를 갖고 있고, 체계가 같다**(법정동코드 앞 5자리 = 시군구 코드).
사용자의 지역코드 하나로 두 데이터를 **각각 거르면 된다.** 정책과 센터를 직접 잇는 단계는 필요 없다.

```
사용자 위치 (주소 / GPS / 직접 선택)
   │  주소 → 법정동코드 10자리 (예: 4146310100)   ※ 지오코딩 API 또는 행안부 법정동코드표
   ▼
시군구 코드 U = 앞 5자리 "41463" (용인시 기흥구),  시도 S = "41"
   │
   ├─▶ 정책: zipCd 안에 U가 들어 있는 정책           (POLICY_FIELDS.md 지역 매칭 참고)
   │        └ 순위: 우리 시군구만 > 우리 시도 > 전국
   │
   └─▶ 센터: stdgCtpvCd + stdgSggCd == U 인 센터
            └ 없으면 같은 시도(S)의 센터 → 좌표가 생기면 거리순으로
                 └ 센터 프로그램(홈페이지 크롤링)은 그 센터의 지역을 그대로 물려받는다
```

| | 정책 | 센터 | 센터 프로그램 |
|---|---|---|---|
| 지역 정보 | `zipCd` (5자리를 쉼표로 여러 개) | `stdgCtpvCd`+`stdgSggCd` (5자리 1개) | API에 없음 → 크롤링 |
| 의미 | **신청자 거주지 요건** | 센터 위치 | 운영 센터 위치 |
| 범위 | 시군구 1개 ~ 전국 | 시군구 1개 | 센터와 같다 |

두 데이터를 잇는 게 의미 있는 경우는 지역 판단이 아니라 **"이 정책 신청을 도와주는 센터"처럼 내용으로 엮을 때**뿐이다. 이건 지금 필요하지 않다.

### 매칭할 때 함정 (자세한 내용은 POLICY_FIELDS.md)

1. **전국 정책이 698건이다.** 지역 정책보다 위로 올라오지 않게 순위를 낮춘다.
2. **"전국"을 나타내는 전용 코드가 없다.** 코드가 240개 이상이면 전국으로 본다. 등록 시점에 따라 목록이 256·254·251개로 다르고, **251개짜리 316건에는 울산이 빠져 있다.** 개수로 판단하지 않으면 울산 사용자에게 316건이 누락된다.
3. **옛 코드와 시 단위 코드가 섞여 있다.** 화성(`41590` → `41591~97`), 천안(`44130` ↔ `44131/44133`), 인천 개편(`28110` 중구 → `28125` 제물포구 등). 사용자 코드에 대응하는 옛 코드와 시 단위 코드도 함께 조회한다.
4. **지자체 정책인데 `zipCd`가 전국인 경우가 175건이다**(예: 대구 "귀환 청년 주거지원"). 다른 지역 사용자에게 보여 줄지 정해야 한다. 등록기관 시도(`rgtrHghrkInstCdNm`)를 함께 보여 주면 된다.
5. **센터는 190개 시군구에만 있다**(정책에 나오는 시군구는 262곳). 센터가 없는 지역은 같은 시도로 넓혀서 보여 준다.

## 수정 이력

- **한글 URL 인코딩 오류 수정**: `http://www.꿈터.kr/`처럼 한글이 들어간 URL에서 `UnicodeEncodeError`가 났다. `to_ascii_url()`을 추가해 한글 도메인은 punycode로, 경로와 쿼리는 퍼센트 인코딩으로 바꾼다. 실패하던 3곳(열림, 꿈터+, 청정지대)이 이제 200으로 접속된다.
- **특화요건 집계 누락 수정**: 실제 응답의 필드명은 `sbizCd`인데 스크립트는 `sBizCd`로 찾고 있었다. 그래서 `special_targets.csv`에 특화요건 분포가 비어 있었다. 지금은 두 이름을 모두 확인한다.
- **센터 페이지 수집 방식 수정**: 처음에는 "중복 30건"으로 보고 지웠다(→ 221건). 원인을 따라가 보니 실제 중복이 아니었다. 페이지를 넘길 때 정렬이 바뀌어 같은 센터가 두 번 오고, 다른 센터 30곳이 빠지고 있었다. 지금은 `pageSize=1000`으로 한 번에 받아 251곳을 모두 수집한다. `cntrSn` 기준 중복 제거는 안전장치로 남겨 두었다.
- **scheme 없는 URL 누락 수정**: `www.hampyeong.go.kr`처럼 `http://`가 없는 URL 4곳(함평군, 광진 청년아지트, 경산시, 청춘곳간)이 진단에서 빠져 있었다. `guess_url()`이 이런 값에 `http://`를 붙이도록 고쳤다. 4곳 모두 200으로 접속되고, 진단 대상이 241곳에서 245곳이 됐다.
- **플랫폼 오분류 수정**: 플랫폼을 HTML 본문에서도 찾았기 때문에, 푸터에 인스타그램 링크만 있는 자체 홈페이지가 "instagram"으로 분류됐다. instagram 133곳 중 107곳이 실제로는 자체 홈페이지였다. 네이버 블로그와 지자체 사이트(본문의 `.do` 링크 하나로도 걸림)도 같은 문제가 있었다. 지금은 외부 플랫폼을 **최종 URL 도메인**으로만 판단한다. HTML 지문은 CMS를 판별할 때만 쓰고, 본문의 SNS 링크는 `sns_links` 칸에 따로 기록한다.
